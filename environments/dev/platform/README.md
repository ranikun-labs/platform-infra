# DEV platform root

Local candidate only; no AWS resources have been created. Configure the S3 backend bucket and region at initialization. State uses `dev/platform/terraform.tfstate`, encryption and S3 lockfiles; provision and authorize the backend separately. Set the mandatory DEV account ID; the provider rejects other accounts. Pass shared root outputs explicitly: VPC, public/private subnets, cluster ARN, namespace ID and matching namespace name. No root reads another state. Provide an issued regional ACM certificate, approved ALB ingress CIDRs, and the verified Gateway readiness path. ALB sends all HTTPS requests to Gateway on 8080 and probes 9091. Verify Cloudflare origin restrictions, route precedence, OAuth and readiness before use.

Gateway and Core are private Fargate services with Cloud Map discovery. Platform owns Gateway-to-Core and ALB-to-Gateway rules. Shared owns database and Valkey ingress rules: pass the platform service security group outputs to its approved ingress maps, and do not grant platform permission to mutate shared security groups. Product roots own their Gateway-to-product rules. The Gateway baseline config sets its application and management ports and the Core auth URI from the service name and namespace; Core's application port is 8081. Configure all remaining real application settings, product routes, secrets and approved authentication explicitly. Verify the static DNS and route contract against deployed application versions; reference authentication is off by default. `dev_dual_auth.enabled` is a DEV-only opt-in that runs one Core for Carelog auth plus Finance reference auth and adds the Gateway Finance route with its JWT and trusted-context settings. Inputs are Secrets Manager ARNs plus `carelog_enrollment_origin`. The Carelog enrollment and product-claims secrets must match Carelog's values, and the Finance trusted-context secret must match the finance root's `dev_trusted_context` secret. Core and Gateway guards reject production markers, but do not enable this outside DEV.

- `carelog_enrollment_origin` is the HTTPS origin of Carelog's enrollment listener (TLS sidecar, port 8443): scheme, host and port only, no path, query or userinfo. Core rejects non-loopback http for enrollment (platform-services f9adfd3), so http is refused here. It feeds `PLATFORM_IDENTITY_CARELOG_ENROLLMENT_BASE_URL` only. `carelog_claims_origin` (http or https origin, product port) feeds `PLATFORM_IDENTITY_PRODUCT_CLAIMS_BASE_URL`, because the TLS listener serves enrollment only. `core_truststore` is the digest-pinned Core trust-init image (built FROM the exact Core image digest with the public Carelog CA baked in). Core reads the derived truststore through `JAVA_TOOL_OPTIONS`, and the app starts only after the init container succeeds. The Gateway's Carelog backend (`PLATFORM_GATEWAY_CARELOG_BE_URI`) stays at its `gateway_runtime` value. Stacked on the dev-carelog branch: the `modules/ecs-service` extensions (`additional_containers`, `app_depends_on`, `additional_ecr_repository_arns`, volumes) land there and must merge first.
- **Pending decision (not resolved here):** Core `f9adfd3` rejects non-loopback `http` for enrollment (`CarelogEnrollmentProperties.java`, `requiredBaseUri`). A DEV `http://` Carelog origin will therefore fail at Core. Choose either a DEV-only Core code relaxation or a private HTTPS origin before enabling. Terraform accepts both schemes, so it does not enforce this.
- `redis_tls_enabled` has no default: it is required when `dev_dual_auth.enabled` is true. Set it to match the Valkey endpoint actually in use. `true` requires a TLS-verified endpoint; see the note below.
- With the opt-in, `SPRING_PROFILES_ACTIVE` is set by dual-auth for Core (`finance-reference,dev`) and Gateway (`finance-trusted-context-reference`). These maps are merged after `runtime.environment`, so any runtime profile value is replaced, not combined.
- With the opt-in, the root also validates that required keys are present (names only): Gateway `PLATFORM_GATEWAY_CARELOG_RAG_URI`, `PLATFORM_GATEWAY_CARELOG_BE_URI`, `PLATFORM_GATEWAY_REDIS_HOST`, `PLATFORM_GATEWAY_REDIS_PORT`, `PLATFORM_GATEWAY_REDIS_KEY_PREFIX`, and secrets `PLATFORM_GATEWAY_INTERNAL_SECRET`, `PLATFORM_GATEWAY_JWT_VERIFICATION_SECRET`; Core `PLATFORM_IDENTITY_REDIS_HOST`, `PLATFORM_IDENTITY_REDIS_PORT`, `PLATFORM_IDENTITY_DATASOURCE_URL`, `PLATFORM_IDENTITY_DATASOURCE_USERNAME`, `PLATFORM_IDENTITY_DATASOURCE_PASSWORD`, `PLATFORM_IDENTITY_JWT_SECRET_KEY` (environment or secrets). Canonical names only; legacy aliases are not accepted here.

Managed Valkey requires TLS. The currently production-wired Platform Core Identity Redis client has not been verified to use TLS, so keep managed Valkey off until separately approved TLS-capable Core and Gateway releases are verified against it. An existing separately verified private cache may be used instead when its connection and security contracts are approved. Do not point the current unverified client at the managed TLS endpoint.

The module creates a baseline task definition and uses it for the first service by default. A previously registered first revision may instead be supplied, but must have the correct Fargate awsvpc configuration, container name, roles and ports. Release automation owns subsequent revisions and must apply baseline changes to newly registered revisions. Terraform ignores subsequent task definition and desired count changes; setting either input later does not update a running service. For a controlled first deployment, both desired counts default to zero; apply platform, then pass its service security groups to shared and apply the approved database/Valkey rules. Once dependencies and runtime configuration are verified, manually set desired counts to one. Manual ECS desired-count changes also support a controlled 0→1 experiment. Coordinate across services and verify work, outbox, drain, readiness and Aurora recovery first. There is no automatic scheduler or request-driven startup: authentication, leases, concurrency, in-flight work, readiness, and shutdown contracts have not been verified.

Audit messaging is disabled unless `audit_contract` names an accepted contract, nonempty alarm actions, and existing producer and consumer roles whose names begin with the DEV platform name prefix. Product-owned producers must receive their own queue-scoped send policy from their owner root, not through this platform role policy. Enabling it creates encrypted SQS/DLQ, role policies and alarms; it does not deploy or claim an active consumer. Establish retry/visibility, idempotency, outbox recovery, redrive and alert ownership before enabling. The age alarm threshold is a 300-second starting value to review against the accepted contract.

# finance DEV root

This root owns only the finance service and its gateway ingress rule. Supply `shared` and `gateway_security_group_id` from reviewed shared/platform outputs; it does not read another state. Supply the expected 12-digit `aws_account_id`; the provider refuses credentials for a different account. Configure an existing encrypted state bucket and region with `terraform init -backend-config=...`; the key is fixed per root and S3 native locking is enabled. Bootstrap and authorize that bucket separately.

Supply the immutable ECR image digest, exact repository ARN, task sizing, actual listening port, health command, environment and ECS secret references for the `finance-harness-be` application. Do not put secret values in environment or Terraform variables/state; `secrets` maps container environment names to ECS-supported Secrets Manager/SSM references. `execution_secret_arns` must include the exact underlying secret/parameter ARNs (without ECS JSON-key suffixes) and `execution_kms_key_arns` any customer-managed decryption keys. App IAM is empty unless an explicitly scoped policy is supplied. Confirm the image contains the health-check command and handles SIGTERM gracefully before deployment. No product queue or cache dependency is assumed. Supply approved application runtime configuration and secret references; do not assume a shared authentication configuration. Trusted-context routing is a DEV-only opt-in: `dev_trusted_context` (off by default) enables the `dev` profile receiver and injects `FINANCE_TRUSTED_CONTEXT_SERVICE_SECRET` from a secret ARN that must be the same secret as platform `dev_dual_auth.finance_trusted_context_secret_arn`. Never enable it with a prod profile or marker. `SPRING_FLYWAY_ENABLED=false` is always set because the release gate requires it, so migrations must run as a separate step before the first task starts (`ddl-auto: validate` fails startup on an unmigrated schema). The DEV readiness probe runs `curl` against the management port 8081 inside the container, so the image must include `curl`.

Terraform creates a baseline task definition; `baseline_task_definition_arn` identifies it. At first creation the service uses it, unless a pre-registered `first_task_definition_arn` is provided. After creation, release automation owns the active service task definition and the scale controller owns desired count; Terraform ignores only those service fields. Terraform still registers a new baseline revision for task configuration changes, but does not deploy it automatically. The release process must compare its revision against the current baseline and explicitly deploy a matching revision whenever task settings change; otherwise the running service can retain stale settings despite a clean plan. Changes to IAM, discovery, network and service rollout remain Terraform-owned. Validate release/rollback and scaling ownership before enabling automation.

The initial desired count defaults to 0 for bootstrap; omit `runtime.initial_desired_count` or explicitly set it to 0. Supply this service security group ID to the shared root for its narrowly scoped database ingress and apply shared; only then start the service through the operational scale controller or manual procedure. Establish and verify the baseline of one task after networking and runtime configuration are ready. Shared owns database ingress; product roles must not mutate shared security groups.

Baseline revisions are retained across Terraform replacement and destroy. Release owners may deregister old revisions only after verifying that no service or other workload references them and the agreed rollback retention period has passed.
